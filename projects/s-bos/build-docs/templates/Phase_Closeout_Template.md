# Phase Closeout: [App Name] — Phase [N]

> ## 🛠️ Read Before Filling
>
> **Template version:** AI-optimized (multi-instance closeout doc; same `_[N]` pattern as Mid-Build Review)
> **Fill order:** Written by the build agent at the end of every phase. Ryan signs it. It becomes the input to the next phase. One file per phase.
>
> **Filename convention:** `[AppName]_Phase_Closeout_[N].md` where `[N]` is the phase number (Phase 1, Phase 2, Phase 3, ...). Not overwritten — each phase gets its own file. The chain forms the project's audit trail.
>
> **Source docs (read every one before writing this Closeout):**
> - `[AppName]_Module_Breakdown.md` — Module Registry, Phase Plan, Acceptance Criteria patterns. Section 2 (Modules Completed) and Section 3 (Acceptance Criteria Verified) pull directly from here.
> - `[AppName]_Progress_Checklist.md` — current state of every module's checkboxes and Status. Section 2 statuses must match what Progress Checklist shows at gate-fire time.
> - `[AppName]_Build_Decisions_Log.md` — every BD-XX added during this phase. Section 4 lists them by type with negative confirmation if none.
> - `[AppName]_Mid_Build_Review_[K].md` files closed during this phase (if any) — unresolved Findings deferred forward from Mid-Build Review instances roll up here.
> - `[AppName]_Phase_Closeout_[N-1].md` (if not first phase) — the previous phase's Closeout is the upstream reference for the "Builds On" section and for any Carried items.
> - All design docs the phase touched — Section 6 (Design Doc Updates Required) requires the agent to know which docs were affected.
>
> **Downstream docs that consume this one (write to feed them):**
> - `[AppName]_Phase_Closeout_[N+1].md` (the next phase's Closeout) — references this one in its "Builds On" section
> - `[AppName]_Project_Closeout.md` — the Project Closeout harvests across the full Phase Closeout chain. Section 3 of Project Closeout (BD Roll-Up), Section 4 (Concerns Raised vs. Resolved), and Section 6 (Template Deltas) all pull from the Closeout chain.
> - **Ryan** — the primary consumer. Closeout is read by a human under decision pressure ("approve and continue, or send back for revision"). Section 8's outstanding-question pattern exists to force the wait.
>
> **Agent role:** Scribe and verifier. The agent assembles the report from source docs (the build state already exists in Progress Checklist, BD Log, etc.). The agent does NOT invent new module statuses, does NOT silently downgrade a 🟠 Open Concern to "resolved" without an explicit BD resolution, and does NOT skip the negative-confirmation rule in Section 4 (if no BD entries were added this phase, the agent must write the explicit "None this phase, justification: [reason]" line).
>
> **The three rules while filling this doc:**
> 1. **Every section is filled — blank is not an answer.** A section with no content gets either real content or an explicit `None — justification: [reason]`. The justification line is required by the negative-confirmation rule.
> 2. **The last line is a question to Ryan, not a statement.** This is structural — statements pass silently, questions force a wait. The pattern comes from a real failure where statements were silently passed over and only questions held. Section 8 enforces this; the agent does not move on without it.
> 3. **Sign-off is binary.** Either Ryan replies "approved" and the phase is closed, or Ryan replies with corrections and the doc is revised before re-asking. No "close enough." No mid-state acceptance.
>
> **Two failure modes this doc is designed to prevent:**
> - **Statement-not-question drift.** A previous failure mode was the build agent ending Closeouts with statements ("Phase 1 complete — proceeding to Phase 2") that Ryan silently passed over. The doc shipped without sign-off. Section 8's hard rule (last line MUST be a question) defeats this.
> - **Silent module closure.** Modules marked ✅ Done in Progress Checklist but without verify-script artifacts, or with acceptance criteria left ambiguous. Section 5's verify-script enforcement ("absence of a verify script for a ✅ Done module means the module is not actually done") makes the gap visible by absence.
>
> **When this Closeout is fully filled and approved:** Remove every `🤖 AGENT INSTRUCTIONS` block. Keep all filled content, every checkbox, every BD reference, Ryan's approval, and the closing question. The finished Closeout reads as the phase's permanent record.
>
> **Cleanup verification (before declaring the Closeout signed off):**
> - Search the file for `🤖` — zero hits
> - Search the file for "Remove this block" — zero hits
> - Every section has content or an explicit `None — justification: ...` line
> - The last line of the doc is a question, not a statement

## How to Use This Doc

This template is enforced, not advisory:

1. **Every section has required content or an explicit `None — justification: [reason]`.** Blank is not an answer. Silence about a section is treated as the section being incomplete.
2. **The last line of this doc is a question to Ryan, never a statement.** This is structural — it's what stops the agent from charging into the next phase. The pattern comes from a real failure where statements were silently passed over and only questions held.
3. **Sign-off is binary.** Either Ryan replies "approved" and the phase is closed, or Ryan replies with corrections and the doc is revised before re-asking.
4. **Don't write the next phase's Closeout until this one is signed off.** Closeouts are not concurrent.
