**Purpose:** A working doc for processing template improvements identified during a project's retro/Project Closeout. Items get triaged by category, worked through one at a time, then reviewed and merged into the canonical templates in the Generic app project docs folder.

**When to use:** When a project's Project Closeout (or ad-hoc retro) produces a list of proposed template changes. Copy this template into the project's folder, rename it `{Project_Name}_Template_Update_Worklog.md`, fill in the items, then work through them with Claude Desktop.

**Update:** Live during the work session. Each item moves: ⏳ Not Started → 🔄 In Progress → ✅ Done. When all items are ✅ Done (or explicitly deferred), the worklog is closed and the canonical templates reflect the changes.

**What this is NOT:** This is not consumed by the next project automatically. Ryan brings completed worklogs back to Claude in a new session, and Claude integrates the changes into the canonical template files in the Generic app project docs folder. The next project starts from clean, updated templates — never from a worklog.

## How to Use This Doc

### Filling it in (post-retro)

1. Read the source retro / Project Closeout / Discussion file.
2. For each proposed template change, decide which category it falls into (A, B, C, or D below).
3. Add the item to the appropriate category table with: parking-lot reference, target file, brief approach, status, notes.
4. If an item doesn't fit any category, add it to the **Scratch Pad** at the bottom and discuss before assigning a category.

### Working through items

1. Pick one item. Update its status to 🔄 In Progress.
2. Discuss the approach with Claude before editing. Concrete approach beats abstract intent.
3. Claude makes the edit to the target template file in the Generic app project docs folder.
4. Ryan reviews the edit on disk. If good, status moves to ✅ Done.
5. Move to the next item.

### Closing the worklog

When all items are ✅ Done or 🚫 Deferred (with reason):

1. Run a quick consistency pass — do the edits hang together, or do some templates now contradict others?
2. Update the worklog header with a closeout note: date, what was merged, what was deferred and why.
3. Commit the canonical templates *and* the closed worklog. The closed worklog is part of the audit trail — don't delete it.

## Working Rules

- **One item at a time.** Don't open three at once.
- **Discuss approach before editing.** "Here's the proposed change, here's why" comes before the file edit, not after.
- **Edit canonical templates directly.** The worklog records intent and status; the actual change lives in the template file. No staging copies, no diffs — direct edit on disk.
- **If a change touches multiple templates, list them all in the item.** Cross-cutting changes are a red flag for inconsistency — handle them deliberately.
- **Defer with reason, not silently.** A 🚫 Deferred item must record *why* it was deferred and what would change to revisit it.
- **Scratch Pad is for genuinely unclassified items.** If you find yourself adding three things to the scratch pad, you've probably found a new category — promote it.

## Status Values

- ⏳ **Not Started** — In the worklog, not yet picked up
- 🔄 **In Progress** — Being discussed or edited right now
- ✅ **Done** — Edit landed in the canonical template, reviewed, approved
- 🚫 **Deferred** — Explicitly punted, with a reason in Notes and a condition for revisit

---

## Recommended Work Order

This isn't a hard rule, but in practice the dependencies between categories tend to suggest:

1. **Category B first** — typology/structural changes get defined, because Categories A and D often reference them.
2. **Category C next** — Instructions touch-ups set tone for the new templates, and they're cheap to ship.
3. **Category A** — net-new artifacts, designed against the now-stable Category B work.
4. **Category D last** (or interleaved with A) — wiring is brittle if the things being wired are still moving.

Override the order if a specific item is urgent or blocks others. The point is to surface dependencies, not to lock the sequence.
